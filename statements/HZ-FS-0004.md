# HZ-FS-0004: Order notifications share one subject, so Gmail threads unrelated inquiries together: anything keyed by thread id mixes orders

**Hazard:** Two unrelated inquiries are read as one: Gmail groups every order notification under the identical subject "Uus Factory.Sale päring", and a lookup, an offer-log row or an automation keyed by the thread id picks the wrong order without noticing.

**Cause:** The shop's notification carries the inquiry number in the body only; Gmail threads by subject and participants ([[FIND-FS-0004]]).

**Details:**
- #249481 and #249493 of 24.08.2026 — different products, different customers — came back as two messages of one thread; the agent isolated the order by the message id ([[FIND-FS-0004]]).
- The offer log's provenance columns are `thread_id` and `message_id` (`fs:data/README.md@89d77d2`, [[ELM-drive.offerLog]]); a `thread_id` is ambiguous by construction.
- Setup item 9, unowned ([[SRC-20260916-ops-open-setup-items#^item-9]]).

**Consequences:**
- The wrong order is read, classified and priced; a fixture keyed by thread id tests the wrong case.
- The problem grows with volume (5–20 inquiries a week, [[FACT-FS-0002]]).

**Check:**
- In Gmail: `subject:"Uus Factory.Sale päring"` — messages per thread (the operator).
- Iteration 2: the inquiry arrives by the Bitrix24 webhook with its own id; no thread id in the state ([[ELM-fs.api]]).

**Mitigation:**
- Key on `Päring #NNNNN` in the body or on the message id, never on the thread id; the offer log keeps `message_id` as the primary provenance.
- Put the inquiry number into the notification's subject on the webshop side (item 9: the developer or the shop admin).
- Iteration 2 takes the inquiry from the Bitrix24 webhook, not from the mail.
