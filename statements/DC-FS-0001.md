# DC-FS-0001: Two separate mailboxes: the sunset of the iteration-1 single-inbox exception

**Change:**
1. A dedicated Gmail for the transport channel (the guide proposes `sales.factorysale@gmail.com`), with sales@factory.sale forwarded into it and the send-as alias added there.
2. Connect it as a second account: the native Gmail connector holds one Google account, so a multi-account MCP server (`workspace-mcp` with Gmail tools, an OAuth client of the company's Google Cloud project) or a shared-inbox tool.
3. Supersede the exception in [[ADR-FS-0009]] with a new decision; retire the labels transport-sales / transport-orders as the separation mechanism.

**Reason:** The native connector's one-account limit forced the iteration-1 merge of both streams into the operator's inbox ([[ELM-mail.gmail]]); the merge mixes order and partner mail, risks a missed partner reply and dirties the ranker's data ([[HZ-FS-0002]]). The separation itself is decided ([[ADR-FS-0009]]).

**Result:** Order intake and partner communication in separate inboxes; the agent's mail scope is a mailbox, not a label; cleaner offer data by construction.

**Constraints:**
- An OAuth client secret on disk of the machine running the MCP server — out of synced and committed folders.
- A `uvx` server to maintain on the operator's machine.
- In iteration 2 the question changes: the service reads the Radicenter mailbox directly ([[ADR-FS-0008]]), and the second Gmail may not be needed at all.

**Revisit trigger:** A self-hosted multi-account MCP server or a shared-inbox tool is ready; or the iteration-1 → 2 gate, where [[ADR-FS-0008]] is decided. The project manager owns the timing ([[SRC-20260913-memo-transfer#^m23]]).
